## 1. 匹配规则(设计决定)

每个 `tx_hash` 是**单价单笔**(7,508 笔实测:无一笔跨 token / 跨方向 / 跨价格),
所以逐笔撮合、不做扫档拆分。对我方买单价 `p`:

```
ahead = 价格优于 p 的挂单量           (QUEUE_FRONT)
        + 恰在 p 的挂单量             (QUEUE_BACK)
fill  = clip(print_size - ahead, 0, our_size)
```

可达性要求 `p >= print_price`(卖方愿意卖到那个价,则其上所有买单都够得着);卖单镜像。

**两个刻意的后果**：

- **报在价差内会成交,即使该价位从未有过成交记录。** 我方挂单是原本不存在的流动性,
  扫到更差价格的 taker 本会先吃到我们。只在"有成交记录的价位"撮合,
  会系统性低估**恰恰是 sizing 最需要定价的激进报价**。
- **报得深会被自动惩罚**,因为 `ahead` 随上方簿子增长。无需额外规则。

队列位置原则上不可观测(簿子按价位聚合 + 60s 快照),沿用 `score.denominator_bounds`
的认识论:**只给区间,不给点估计**。前/后两端即诚实的不确定性宽度,不得取中值。

## 2. 磁带 side 语义 —— 已实测钉死

不是猜的。`tape_side_evidence()` 用价格 vs 最优买卖价做交叉表(08-23,1,163 笔):

| | 计数 |
|---|---|
| BUY 且价格 ≥ 最优卖价 | 301 |
| SELL 且价格 ≤ 最优买价 | 586 |
| BUY 且价格 ≤ 最优买价(反例) | 7 |
| SELL 且价格 ≥ 最优卖价(反例) | 7 |

**价格触及卖价的 97.7% 标为 BUY,触及买价的 98.8% 标为 SELL
→ `side` 是 taker 方向,`tape_is_taker=True` 正确。**
约 2% 反例可由快照最长 60s 陈旧解释。

## 4. ⚠️ 新发现:60 秒盲区(重要,且不可回溯修复)

`over_book` ≈ 23%。**原以为是 band 过滤所致 —— 实测证伪**:
在 `books_full` 上重跑 `v1_reconcile`,over_book **完全相同**(08-25 窗口内 12/64,两者一致)。

08-23 的 332 笔 over_book 拆解:

| 成因 | 笔数 | 占比 |
|---|---|---|
| **成交价在被吃一侧最优价之内** | **254** | **77%** |
| 扫穿最优价、进入未记录的深度 | 47 | 14% |
| 就在最优价,但大于所记录的该档量 | 31 | 9% |
| (其中可用深度为零) | 274 | |

主因是**在两次 60s 快照之间被挂出并被吃掉的流动性** —— 该采样频率下原理上不可见,
且**无法回溯修复**(不是 books_full 能解决的问题,books_full 解决的是 band 外深度,
用于 P2 平仓成本,那个用途不受影响)。

**为什么这重要**:这批成交系统性地发生在激进价位,
**正是我方激进报价要去竞争的那一群**。因此:

> **本模块算出的成交率是下界。诚实的报告区间是
> [仅已撮合, 已撮合 + 全部价差内成交]。**

已写进 `shadow.py` 模块 docstring,后续任何成交率结论必须带这个区间。

### 开发中被测试抓到的一次自造错误

`test_flipping_the_tape_convention_flips_which_side_fills` 最初断言同一笔成交在两种
语义下分别落在买、卖两侧 —— **该断言本身不成立**:能够到我方买单的价格,
按构造必然够不到我方卖单(除非报价交叉)。是测试写错了,不是代码错。
改为"一笔成交、一个挂单、两种语义"后通过,并把这个几何约束写进了测试 docstring。

## 6. 明确未做(留给后续层)

存货、逆向选择、自身冲击重算中价、奖励打分、再报价/撤单 —— 均不在本模块。

一个已知答案(V1)做验证。
